# Inception

## Description

Inception is a system administration project: a small web infrastructure built
with Docker Compose inside a virtual machine. It serves a WordPress website over
HTTPS at `https://joafern2.42.fr`, using three services, each in its own
container and built from its own Dockerfile:

| Service | Role | Port (internal) |
|---|---|---|
| `nginx` | Web server, TLS termination, the only entry point | 443 (published) |
| `wordpress` | WordPress run by php-fpm (no web server) | 9000 |
| `mariadb` | Database storing the site's content | 3306 |

A request travels from the browser to NGINX on port 443. NGINX serves static
files itself and passes PHP requests to php-fpm in the WordPress container on
port 9000. WordPress reads and writes its content in MariaDB on port 3306. Only
port 443 is published; the other two services are reachable only inside the
private Docker network.

### Use of Docker and sources included

Every image is built from `debian:bookworm`; no ready-made service image is
pulled. The repository contains:

```
.
├── Makefile                 # builds and runs the whole stack
├── secrets/                 # password files, generated by make (not in Git)
└── srcs/
    ├── docker-compose.yml   # services, volumes, network, secrets
    ├── .env                 # non-secret settings (committed)
    └── requirements/
        ├── mariadb/
        │   ├── Dockerfile
        │   ├── conf/50-server.cnf   # server and client settings
        │   └── tools/init.sh        # first-start setup, then runs mariadbd
        ├── wordpress/
        │   ├── Dockerfile
        │   ├── conf/www.conf        # php-fpm pool listening on port 9000
        │   └── tools/setup.sh       # waits for MariaDB, installs WordPress
        └── nginx/
            ├── Dockerfile
            ├── conf/inception.conf  # HTTPS server block
            └── tools/start.sh       # creates the certificate, runs NGINX
```

Each `Dockerfile` installs only what its service needs and copies in its config
and startup script. Each startup script prepares the service and finishes with
`exec`, so that the service itself becomes PID 1 and runs in the foreground.

### Design choices

- **Base image:** Debian 12 (bookworm), the penultimate stable Debian release,
  named explicitly instead of using the `latest` tag.
- **One startup script per service.** Setup that needs passwords, environment
  variables or volumes cannot happen at build time, because those only exist
  when a container starts. The scripts detect the first start (MariaDB checks
  for the database folder, WordPress for `wp-config.php`) and skip setup on
  later starts, so restarts never touch existing data.
- **PID 1:** every script ends with `exec`, replacing the shell with the
  service. The service receives Docker's stop signal directly and shuts down
  cleanly. No `tail -f`, `sleep infinity` or similar is used.
- **Waiting for the database:** `depends_on` only orders container starts. The
  WordPress script therefore pings MariaDB with `mariadb-admin` before
  installing, up to 30 times, then gives up so the restart policy can retry.
  The loop ends as soon as the database answers, so it does not keep the
  container alive.
- **Unattended WordPress install:** WP-CLI downloads WordPress, writes
  `wp-config.php`, installs the site and creates both users from the command
  line.
- **TLS certificate generated at container start,** not at build time, so the
  private key is never stored in an image layer, and its name comes from
  `DOMAIN_NAME` in `.env`. NGINX accepts TLSv1.2 and TLSv1.3 only and has no
  port 80.
- **Least privilege:** each container receives only the secrets it uses (NGINX
  none, WordPress no database root password), the database is used by
  WordPress through a dedicated non-root account, and services run their work
  as unprivileged users (`www-data` for PHP and NGINX workers).
- **Configuration in Git, passwords out of it:** `srcs/.env` is committed
  because it holds only non-secret configuration (domain, database name,
  usernames, site title). Every password lives in `secrets/`, which the
  Makefile generates locally with `openssl rand` and which is never committed.
  The password files are created only if they do not exist yet, so a fresh
  clone runs with a single `make`. Secrets and data are always deleted
  together by `make fclean`, so the passwords on disk always match the ones
  stored in the database.
- **Logs:** NGINX's log files are linked to the container's standard output and
  error, so they appear in `docker logs`.
- **Restart policy:** `unless-stopped`, so containers come back after a crash or
  a VM reboot, unless they were stopped on purpose.

### Virtual Machines vs Docker

A virtual machine emulates a whole computer: it boots its own operating system
with its own kernel, from an installer, and takes minutes to set up and start.
A container is a group of isolated processes running on the host's kernel. It
packages only an application and its files, so it starts in about a second and
uses far fewer resources. The trade-off is isolation: a VM is separated from
its host at the hardware level, while containers share one kernel. This project
uses both: the VM provides an isolated, reproducible Linux machine, and Docker
runs each service inside it as a lightweight, disposable container.

### Secrets vs Environment Variables

Environment variables are visible to anyone who can inspect a container
(`docker inspect`, `env` inside it), and `env_file` gives every variable in the
file to every container that loads it. Secrets are delivered as read-only files
under `/run/secrets/`, only to the services that list them, and never appear in
the container's configuration. This project therefore keeps passwords in
`secrets/` (database root password, database user password, WordPress user
passwords), which is excluded from Git, and non-sensitive settings such as the
domain and usernames in `.env`.

### Docker Network vs Host Network

On a user-defined bridge network, like this project's `inception` network,
containers get their own private network: they reach each other by service name
(`mariadb:3306`, `wordpress:9000`), and nothing is reachable from outside unless
a port is explicitly published. With `network: host`, a container shares the
host's network directly: its ports open on the host without any `ports:` line,
there is no isolation between it and the machine, and containers cannot find
each other by name. Host networking would expose MariaDB and php-fpm directly
and break the rule that NGINX on port 443 is the only entry point, which is why
the subject forbids it.

### Docker Volumes vs Bind Mounts

A bind mount attaches a host path straight into a container. Docker does not
manage it, and the service refers to the raw path. A named volume is created
and managed by Docker, listed by `docker volume ls`, and referred to by name.
This project uses two named volumes (`mariadb_data` and `wordpress_data`). Their
`local` driver options tell Docker to store their data in
`/home/joafern2/data/mariadb` and `/home/joafern2/data/wordpress`, as the subject
requires, but they remain named volumes: Docker creates them, and the services
use them by name. Removing a volume only removes Docker's record of it, so the
data folders are deleted separately by `make fclean`.

## Instructions

### Prerequisites

- A Linux virtual machine (developed on Debian 12)
- Docker Engine with the Docker Compose plugin
- `make`, `openssl` and `sudo`

### Configuration (optional)

The settings live in `srcs/.env`: domain, database name and user, site title,
and the two WordPress users. The administrator's name must not contain "admin",
and the two email addresses must differ. To change a setting, edit `srcs/.env`
before the first `make`, or run `make re` afterwards, since WordPress stores
these values in its database at installation.

### Build and run

```bash
make
```

On its first run, `make`:

1. adds `127.0.0.1 joafern2.42.fr` to `/etc/hosts` if it is missing (asks for the
   `sudo` password);
2. generates the three password files in `secrets/` with `openssl rand`, if they
   do not exist (`credentials.txt` holds the WordPress administrator's password
   on line 1 and the second user's on line 2);
3. creates the data folders in `/home/joafern2/data`;
4. builds the three images and starts the stack.

Existing files are never overwritten, so later runs only start the stack.

| Command | Effect |
|---|---|
| `make` | Set up everything listed above and start the stack |
| `make stop` / `make start` | Stop or restart the containers without removing them |
| `make down` | Stop and remove the containers and the network |
| `make clean` | `down`, then remove unused Docker objects and build cache |
| `make fclean` | Remove containers, images, volumes, the data folders and `secrets/` |
| `make re` | `fclean`, then `make`: a full rebuild from scratch with new passwords |

### Access

The site is available at `https://joafern2.42.fr`, and the administration panel
at `https://joafern2.42.fr/wp-admin`. The certificate is self-signed, so the
browser shows a warning that must be accepted.

To open the site from a browser outside the VM, add the same hosts line to that
machine's hosts file (on Windows, `C:\Windows\System32\drivers\etc\hosts`) and
forward port 443 to the VM.

See `USER_DOC.md` for day-to-day use and `DEV_DOC.md` for development details.
